# Cómo funciona una Web API

Antes de escribir un solo controller.

Antes de hablar de repositorios, patrones, o arquitectura.

Necesitas entender qué pasa cuando alguien hace esto:

```
GET https://tuapp.com/api/productos/5
```

Porque si no lo entiendes, los patrones que vienen después no van a tener sentido.

---

## Qué es HTTP

HTTP es el idioma que usan los navegadores y las apps para pedirse cosas.

Cuando tu frontend hace una llamada a tu API, está enviando un mensaje con esta estructura:

```
VERBO  /ruta  HTTP/1.1
Host: tuapp.com
Authorization: Bearer eyJ...
Content-Type: application/json

{ "nombre": "Laptop" }   ← esto es el body (solo en POST/PUT)
```

El **verbo** dice qué quieres hacer:

| Verbo | Significa |
|---|---|
| `GET` | Dame información |
| `POST` | Crea algo nuevo |
| `PUT` | Actualiza algo |
| `DELETE` | Elimina algo |

La **ruta** dice dónde. El **body** trae los datos si los necesitas.

Y la API responde con esto:

```
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 5, "nombre": "Laptop", "precio": 999.99 }
```

El número `200` es el **status code** — le dice al cliente si todo salió bien o qué salió mal.

| Código | Significa |
|---|---|
| `200` | OK — todo bien |
| `201` | Created — se creó algo |
| `400` | Bad Request — mandaste algo mal |
| `401` | Unauthorized — no estás autenticado |
| `403` | Forbidden — estás autenticado pero no tienes permiso |
| `404` | Not Found — no existe |
| `500` | Internal Server Error — algo explotó adentro |

*El 500 es el que te despierta a las 3am.*

## Qué es una Web API en .NET

Una Web API es una aplicación que escucha requests HTTP y devuelve respuestas.

En .NET, esa aplicación corre sobre **ASP.NET Core** — el framework que construye el servidor, el pipeline, y todo lo que necesitas para recibir y responder requests.

Cuando corres tu proyecto con `dotnet run`, pasa esto:

1. .NET levanta un servidor llamado **Kestrel**
2. Kestrel empieza a escuchar en un puerto — por defecto `5000` o `5001` (HTTPS)
3. Cada vez que llega un request, lo pasa por el **pipeline de middleware**
4. Al final del pipeline está tu controller, que ejecuta la lógica

El **middleware** es código que se ejecuta antes y después de tu controller. Puedes pensar en él como una cadena de filtros — cada uno puede leer el request, modificarlo, o cortarlo antes de que llegue más lejos.

:::tip El middleware es bidireccional
El request baja por el pipeline. La response sube por el mismo pipeline de regreso. Un middleware puede actuar en los dos momentos — antes de que el controller responda y después.
:::

## Tu primer Program.cs

Cuando creas un proyecto nuevo con `dotnet new webapi`, el `Program.cs` se ve así:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Registrar servicios en el contenedor de DI
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();

var app = builder.Build();

// Configurar el pipeline de middleware
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Hay dos partes separadas y eso es intencional.

**`builder.Services`** — aquí registras todo lo que tu app necesita. Repositorios, servicios, DbContext, autenticación. Es el contenedor de Inyección de Dependencias. Antes de que la app arranque.

**`app.Use...`** — aquí configuras el pipeline. El orden importa. Siempre. Si pones `UseAuthorization` antes de `UseAuthentication`, la autorización no va a saber quién eres.

*El orden del middleware es uno de esos bugs que encuentras dos horas después de haberlo introducido.*

## Cómo .NET sabe a qué controller enviar el request

Cuando llega `GET /api/productos/5`, el **routing** inspecciona la URL y busca un controller que tenga esa ruta registrada.

En .NET lo registras con atributos:

```csharp
[ApiController]
[Route("api/[controller]")]
public class ProductosController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ActionResult<Producto>> GetProducto(int id)
    {
        // aquí va tu lógica
    }
}
```

`[Route("api/[controller]")]` — el `[controller]` se reemplaza automáticamente por el nombre de la clase sin el sufijo `Controller`. Entonces `ProductosController` → `api/productos`.

`[HttpGet("{id}")]` — este endpoint responde a `GET /api/productos/{cualquier número}`.

Cuando llega `GET /api/productos/5`, .NET:
1. Ve que es un `GET`
2. Busca un controller con ruta `api/productos`
3. Busca un método con `[HttpGet("{id}")]`
4. Extrae `5` del URL y lo pasa como parámetro `id`
5. Ejecuta el método

Todo eso antes de que tu código corra una sola línea.

## La respuesta — ActionResult

Tu controller no devuelve el objeto directo. Devuelve un `ActionResult<T>`:

```csharp
public async Task<ActionResult<Producto>> GetProducto(int id)
{
    var producto = await repo.GetByIdAsync(id);

    if (producto == null)
        return NotFound();       // 404

    return Ok(producto);         // 200 + JSON
}
```

`ActionResult<T>` te deja devolver tanto el objeto como el status code. Sin él, tendrías que serializar el JSON tú mismo y construir la respuesta HTTP a mano.

Dos. No uno.

Siempre tienes las dos cosas — el dato y el código.

---

## Lo que el cliente recibe

Cuando devuelves `Ok(producto)`, ASP.NET Core:

1. Serializa `producto` a JSON automáticamente
2. Agrega el header `Content-Type: application/json`
3. Pone el status code `200`
4. Envía todo de vuelta por Kestrel al cliente

El cliente recibe esto:

```json
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 5,
  "nombre": "Laptop",
  "precio": 999.99
}
```

Sin que tú hayas escrito una sola línea de serialización.

---

## El resumen en una línea

Cliente manda HTTP → Kestrel recibe → middleware filtra → routing decide → controller ejecuta → response sube de vuelta.

Eso es todo.

Lo que viene ahora — controllers, rutas, DTOs, middleware — es expandir cada uno de esos pasos con detalle.

Pero el flujo no cambia. Nunca cambia.
